# Browser Observation vs. HTTP Download

Two independent captures were compared:

| Capture | Tool | Output |
| --- | --- | --- |
| **A — Browser** (source of truth) | Real Chrome via `playwright-core` | `reference-download/html/rendered-home.html`, `docs/net-home.json`, `docs/outline-home.json`, `docs/tree-all.txt`, `docs/content.txt`, `docs/cms.json`, `docs/shots/*.png` |
| **B — HTTP download** (secondary) | `curl` (HTTrack and wget are not installed on this machine) | `reference-download/html/index.html` (224 KB), `reference-download/css/main.min.css` (128 KB), `reference-download/js/custom-main.js` (59 KB) |

## Verdict

The Webflow HTML is **statically complete** — all copy, all collection-list items and all
image `src`/`srcset` values are present in the downloaded document. What the download
*cannot* tell you is everything that matters visually: the fluid `1vw` root sizing only
resolves at runtime, `SplitText` invents the `.split-word` / `.split-char` DOM at load,
and every scroll choreography lives in a lazily `import()`-ed module. So the download was
useful for **content and tokens**; the browser was the authority on **behaviour**.

## Where they disagreed

1. **Type sizes.** The stylesheet declares `calc(192rem/16)`, which reads as a fixed 192px.
   Only the browser reveals `html{font-size:1vw}`, making it `12vw`. Browser wins.
2. **Heading DOM.** The download has `<h1 class="h1">Era <br>Residence</h1>`; the browser
   shows it split into per-word/per-char spans. Browser wins — the reveal needs them.
3. **Effective image variant.** Markup lists four `srcset` entries; the browser picks
   `-p-1600` at 1440px. Browser wins — that is what we downloaded.
4. **Section 8 height.** The static layout implies ~900px; the browser reports a 2 970px
   scroll area because ScrollTrigger pins it. Browser wins.
5. **Lottie asset.** Absent from the HTML entirely; found only in the network log.
